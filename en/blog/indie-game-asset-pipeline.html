An indie game art pipeline: from source files to a shippable build

A small indie project as the running example: folder structure, naming rules, how the four workspaces divide the work, engine integration and a pre-release checklist.

Workflow2026-11-11·3 min read

Key takeaways

  • Fix folders and naming first; tools come second
  • Four workspaces for four jobs — do not mix them
  • Replace memory with a pre-release checklist

Small teams rarely lack tools; they lack conventions. In one project, someone uses Chinese names, someone uses spaces, someone mixes source files with exports. By release time, finding an image costs more than making one.

Fix folders and naming first

Keep sources and outputs completely separate: sources in art_src, exports in build_art, and never edit either by hand in the wrong place. Organize by asset type, not by person.

art_src/
  characters/
  ui/
  environment/
build_art/
  characters/
  ui/
  environment/

Naming should reveal purpose and variant at a glance: type_name_state_index. Avoid spaces and localized punctuation, and avoid mixed case, because file systems and engines disagree about case sensitivity.

How the four workspaces divide work

TexForge's four workspaces map to four jobs; mixing them makes configuration hard to reuse:

  • Game pixel tools: normal maps, channel packing, mipmaps and engine folder planning — assets that need computation.
  • Batch: size, format, watermark and metadata rules — the need for consistency.
  • Atlas toolbox: nine-patch slicing, sprite splitting and validation — splitting and checking.
  • Atlas: layout and multi-format export — combining and shipping.

From source art to the engine

A typical order: batch-unify size and color, generate normals or pack channels, build atlases and descriptors, then write into the engine folder tree. Save each preset so next time you only change the input folder.

On the engine side, import the folder once and overwrite on updates. Descriptors living next to the atlas image with matching names eliminates most “imported but not found” issues.

Versioning and rollback

Assets belong in version control, but do not commit intermediates. Commit sources, presets and final exports; ignore intermediate files. Tag each release so you can identify exactly which asset change caused a problem.

Only a pipeline you can roll back is safe to ship from frequently.

Pre-release checklist

  1. Do dimensions fit platform limits, and do they need to be POT?
  2. Do atlas descriptors match the images, with verified coordinates?
  3. Are normal maps treated as linear data, with the correct Y axis?
  4. Are private metadata fields stripped and copyright written?
  5. Is the build within budget, and were compression results spot-checked?
  6. Did you run it on a target device to confirm no offset or blur?

Takeaway

A pipeline's value is not how powerful the tool is, but that someone else can run it and that it still works next month. Fix folders, naming, presets and checklists, and the tool finally saves real time.
