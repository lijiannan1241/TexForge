24 engine data formats: export for Unity, Godot, Unreal and Cocos at once

The same atlas needs different descriptors and folder layouts per engine. A look at 24 formats, folder planning and custom templates.

Engine export2026-09-16·3 min read

Key takeaways

  • The descriptor format decides whether the engine sees the atlas
  • Folder layout is a more common failure than the files
  • Custom templates cover in-house engines

Atlas packing is often treated as “generate one big image”. What the engine actually reads is the descriptor: each sprite's rectangle, rotation flag, trim offset and original size. Correct image plus wrong descriptor still renders as a broken layout.

Why 24 formats

Every engine carries its own conventions. Unity sprite data must match its importer; Godot 3 and Godot 4 use different resource formats; Unreal has its own sprite definitions; Cocos, Phaser, PixiJS, Spine, LibGDX, SpriteKit, Starling, Egret, LayaAir and WeChat mini games each differ. Generic JSON, XML, plist, CSS and CSV serve in-house or lightweight runtimes.

Maintaining these by hand is pointless: field names, coordinate origin, rotation support and trim handling each introduce a way to break a whole batch.

Folder layout matters just as much

Most projects do not just drop an atlas into a folder. Unity commonly expects Assets/Art/Atlases with .meta files; Unreal has Content conventions; Godot keeps resources and import settings together. TexForge ships five folder trees — Unity, Unreal, Godot, Cocos and custom — and writes files into the target structure.

The most common failure in an asset pipeline is not a wrong image; it is a file in the wrong place.

Multiple engines in parallel

Shipping Unity and web builds from one project is normal. The same character art feeds two runtimes with different descriptors. A batch can process the source images once and export both formats into their own folders, avoiding manual copying and renaming.

Custom templates

In-house engines and internal specs usually fall outside the 24. Custom templates let you assemble output field by field, keeping the rectangles, offsets and flags you need and dropping the rest. Once fixed, a template is reusable like a preset.

Practical advice

  1. Confirm the target engine's major version first; version differences often hurt more than engine differences.
  2. Put folder trees and naming rules into presets instead of arranging files by hand.
  3. Import once in the engine after export to verify coordinates and trimming.
  4. Keep descriptors in version control so you can find which change broke placement.

Takeaway

An atlas is an image plus metadata; neither works alone. Choosing the right format, placing files correctly and keeping reusable templates is what actually gets assets into the engine.
