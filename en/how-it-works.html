How it works

Four stages, one pipeline. Each stage can be checked on its own, and the whole chain can be handed to a script — that is what makes it usable in production over time.

How data flows

Sources enter one processing chain: action sequence or atlas algorithm, then constraint validation, then format export and reporting. The GUI and the CLI are just two doors into that chain.

Sources / folders→Actions · atlas params→Validation→Export · descriptors→Result report
01

Import and scan

Drop folders or individual images into a workspace. TexForge scans subdirectories recursively and filters by extension, naming rules and size range, so you see exactly what is about to be processed.

  • Mix several folders, including nested subdirectories
  • Filter by extension, wildcard or regular expression
  • Immediate counts, total size and dimension distribution
  • The scan stage is read-only; sources are untouched
02

Configure actions and parameters

Stack actions for batch work, or set layout, padding, trimming and target format for atlases. Save the result as a preset (JSON) — the smallest reusable unit a team can share.

  • 113 actions applied in order, each output feeding the next
  • Atlas parameters: padding, extrusion, trimming, rotation, POT constraints
  • Presets travel with the project and can live in version control
  • The same preset is read by both the GUI and the CLI
03

Preview and validate

See the result before exporting. Atlases show a layout preview and occupancy, batch runs offer a per-image comparison, and constraint checks flag oversized textures, inconsistent padding and empty regions early.

  • Atlas layout preview with sprite positions and occupancy
  • POT / NPOT, maximum size and padding consistency checks
  • Normal maps stay on the linear data path
  • Violations are flagged before export, not after an engine error
04

Export and report

One run produces images, descriptors and a result report. Atlas image and descriptor share a name and folder, so the engine resolves them immediately; the report records what happened to every image.

  • 24 engine data formats written into planned folder trees
  • Atlas image and descriptor generated as a matched pair
  • CSV / JSON reports: successes, failures, timings and size deltas
  • Retry failed items only, never the whole batch

One core, two entry points

The UI is not a separate implementation. GUI and CLI call the same action registry, atlas packer, exporters and report format, so what you tune in the interface is what runs on a server.

One action registry

Both entry points read the same action definitions and parameter validation, so a preset cannot work in the GUI and fail in a script.

One preset file

A preset is JSON. Commit it, and anyone who checks out the project reproduces the same asset release.

One report format

Both produce the same report structure, parsed and archived by the same scripts.

Command line and CI

Hand the preset to texforge-cli to reproduce the same result in a script, on a build server or in CI. Exit codes carry pass/fail; reports are archived as build artifacts.

# Run a batch with a preset saved in the GUI
texforge-cli batch --preset ui-icons.json --input ./art/ui --output ./build/ui

# Pack an atlas and export the engine descriptor plus a report
texforge-cli atlas --preset atlas-ui.json --format unity --report build/report.json
  • Presets, actions and parameters match the GUI exactly — no second configuration
  • A non-zero exit code means some items failed, so CI can gate on it
  • Reports archive as build artifacts, so any release can be audited later

Why it is split this way

Every stage is checkable

Import, configure, validate and export are decoupled, so a problem points at a stage instead of hiding inside a black-box script.

Configuration is separated from execution

Configuration becomes a preset; execution is the GUI or the CLI. The same spec can be run by a person, a machine, or whoever joins next.

Results are verifiable

The report records what happened to each image. A release is documented, not assumed.

A pre-release pass worth running

  1. Validate the preset on 5 to 10 representative images first: dimensions, naming, file size
  2. Confirm atlas descriptor and image share a name and folder, with matching coordinates
  3. Export normal maps as linear data with the Y axis matching your engine
  4. Run a platform size check and confirm no texture exceeds the limit
  5. Archive the report and preset as the record of this asset release
