命令行与 CI 集成：把资源流水线接进构建

GUI 与 CLI 共用同一套管线。用 texforge-cli、JSON 报告与退出码，把资源处理变成构建中的可验证步骤。

自动化2026-10-07·3 分钟阅读

核心要点

  • GUI 调好的预设可直接被 CLI 复用
  • JSON 报告适合做门禁
  • 退出码决定 CI 是否失败

资源处理如果只存在于某个人电脑上的图形界面里，它就是不可复现的。CI 需要的是确定性：同样的输入、同样的命令、同样的输出，失败时能明确报错。

同一套管线，两种入口

TexForge 的 GUI 与 CLI 共用同一套动作、图集参数与预设。这一点很关键：美术在界面里调好的预设，技术美术可以直接在脚本里调用，不需要「翻译」一遍参数。

常见用法是把预设提交到仓库，CI 拉取后用命令行执行，产出图集与描述文件，再交给引擎构建。

命令行能做什么

  • 对整个目录批量执行动作序列，输出到指定目录。
  • 生成图集图片与指定格式的描述文件。
  • 导出资产审查报告，按命名、尺寸、重复与配对规则检查。
  • 输出 JSON 结果，便于后续脚本解析。
texforge-cli --help
texforge-cli batch --preset ui-slices --input ./art --output ./build/art

把报告变成门禁

资源问题的可怕之处是「不报错但难看」。图集里少一个精灵、某个图标尺寸不对，构建照样通过，直到测试才发现。把审查报告接进 CI，可以在合并前拦住这类问题。

做法是让 CI 解析 JSON 报告，按严重级别决定是否失败：错误级直接失败，警告级输出到构建日志，信息级仅记录。规则由团队定，但判定必须自动化。

退出码与幂等

CI 判断成功与否依赖退出码，而不是日志里有没有「Error」字样。批处理任务应在存在未处理失败项时返回非零退出码，让流水线明确停下来。

同时要保证幂等：同一份输入重复执行，输出应完全一致。否则每次构建都会产生无意义的二进制差异，版本库很快被噪声淹没。

落地建议

  1. 把预设与目录规范一起入库，作为资源合同。
  2. CI 中先跑小样本冒烟，再跑全量。
  3. 报告与产物一起归档，便于追溯某次构建用了什么配置。
  4. 给资源任务设置超时与并发上限，避免拖垮构建机。

小结

把资源处理放进 CI，真正的收益不是「自动跑」，而是「每次都用同一套规则跑，并且跑坏了会被发现」。这才是流水线该有的样子。
